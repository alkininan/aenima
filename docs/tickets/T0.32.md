# T0.32 — Generate the build log's current state

**Epic** E0.2 Pipeline · **Type** Technical · **Priority** Medium
**Spec** product-spec v1.8 §5 · build-log Current state · scripts/run/log-index.mjs, version-drift.mjs

## Objective

The build log opens with a Current state written by hand, and it has drifted: main's copy still
says "Next ticket: T3.1", product-spec v1.5 and design-spec v2.17, while the board cites v1.8 and
v2.21 and T3.2 is Ready. Every fresh chat that reads it starts from the wrong picture. The ticket
list below it cannot drift — `log-index.mjs` writes it and its test refuses a stale copy. Current
state should be the same kind of thing; §5 says so outright: "a stamp a human maintains is a stamp
that is eventually wrong."

## Build

1. `log-index.mjs` writes Current state from the repo alone: the version each of product-spec,
   design-spec and guidelines carries in its own header, and the newest `docs/log/` entry with its
   date and commit. The repo and deploy lines stay as they are.
2. "Phase" and "Next ticket" go: the board owns the queue and the roadmap owns phases, and a copy
   here is the drift this removes.
3. The narrative paragraphs under Current state are history. Each moves to the `docs/log/` entry it
   summarizes where that entry doesn't already carry it; nothing is dropped that no other file
   holds.
4. Its test refuses a stale Current state exactly as it refuses a stale list.

## Rules

- From the repo only, never the board: `log-index.mjs` runs at step 8 and in tests, where the repo
  is the record
- Versions are read through the same function `version-drift.mjs` uses — one parser, not a second
- Edit the files, never the generated block — the rule the list already carries

## Criteria

- **AC1** Current state names product-spec, design-spec and guidelines at the versions their own
  headers carry, and the newest `docs/log/` entry with its date and commit
- **AC2** No "Phase" or "Next ticket" line remains
- **AC3** The test fails when a version or the newest entry in the block disagrees with the repo
- **AC4** Every narrative sentence removed from Current state is present in a `docs/log/` entry or
  a spec's own header comment
- **AC5** `log-index.mjs` and `version-drift.mjs` read versions through one shared function

## Tests

- **TC3 → AC3** — reddened by hand-editing a version in the block
- **TC4 → AC4** — one grep per moved sentence

## Cited

### product-spec §5 — Scoring engine

## 5. Scoring engine

Each active artifact is scored against its rubric: 0–100, weights zero-sum per rubric, each check tagged **Must** (blocks handover) or **Should** (advisory).

- **Checks are binary with evidence.** A check passes or fails, and a failure quotes the exact gap ("MN-2: 'nearby' — same venue, or within 100 m? Two readings possible."). No vibes-based partial credit.
- **Event-driven re-scoring.** Notion webhooks where available, short-interval polling where not (Figma), debounced so an edit burst triggers one run, plus a nightly full sweep as backstop. Timestamps show freshness ("scored 4 min ago"); a queued retry shows "scored 6 h ago — retrying" during provider outages, never an error banner.
- **Stability.** Results cache per artifact version; only checks whose artifact changed re-run. The scoring model is pinned per workspace and never juggled for cost. Switching AI provider or editing a rubric triggers a quiet re-baseline pass so numbers never wobble without explanation.
- **Rubrics are versioned** like documents. Every scoring run stamps provider + model + rubric version + **protocol version**. Rubric edits ship through skill packs (below) with the same re-baseline.
- **The protocol is versioned like the rubric, and is part of the cache key.** The protocol is the instruction layer wrapped around a rubric — how to answer, what counts as a quote, that a check is binary rather than partial. It changes verdicts as surely as a check's wording does, so a run scored under one protocol is not comparable to a run scored under another and must not be served from the cache to it. Its version is **computed from the assembled context, never declared**: an edit to the protocol, or to any renderer that shapes what the model is sent, moves the number by itself rather than waiting for someone to remember to bump it. A stamp a human maintains is a stamp that is eventually wrong.
- **Checks are expensive and few; probes are free and infinite.** A rubric stays ~10–20 checks; behind each check sits an open-ended probe library of follow-up questions. Any new check — including ones promoted from the probe library by the learning loop — must take its points from an existing check. This zero-sum budget is what keeps the standard holdable in a human head.

**Negotiation protocol.** Talking the AI into a state change is legal and structured. Persuasion resolves into exactly three typed moves; rhetoric that maps to none of them changes nothing:

1. **"Doesn't apply here"** → applicability re-check. If the condition genuinely fails, the check leaves the denominator.
2. **"Already covered"** → user points at evidence; the pinned scorer re-runs the check against it. Pass → closed with the evidence linked. Fail → the exact remaining gap is shown.
3. **"We accept this risk"** → never closes the gap; converts it to an accepted gap stamped with the accepter's name, routed through the Decider if handover-blocking.

Patterns change the law, not the verdict: when a workspace repeatedly accepts or excludes the same check, the agent proposes a rubric change (versioned, Owner-approved) — it never quietly loosens.
