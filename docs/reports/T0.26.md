# T0.26 — Applied migrations merge themselves

## ACs implemented

- **AC1 — a diff adding a migration whose thread carries a consumed *apply* for that file
  self-merges on a reviewer PASS.** `gatedDiff` takes a migration off the gated list when its tag
  is among the thread's spent applies, and the bookkeeping beside it — the journal and
  `db:generate`'s snapshot — goes with the migrations it records (`scripts/run/gated.mjs`,
  `coveredBy`, `isBookkeeping`). The tags reach it from two places and one source: the guard's
  door through `verify`'s own fetch (`permission.mjs`, `guard.mjs` `judge`), and the skill's step
  9 through `consumedApplies` from a command line. Tested by `gated.test.mjs` "lets the migration
  and its journal entry through once the apply is spent", "lets a snapshot through with the
  migration it records", "lets a migration through on the tag its thread says is applied" (end to
  end over a real repository), `comments.test.mjs` "reads the tag the run's applied note names,
  once the word granted it", `consumedApplies` "answers with the tags the claimed task's thread
  says are spent", `permission.test.mjs` "hands back the tags the thread's applied note names,
  beside the word", `guard.test.mjs` "hands the thread's spent applies to the reviewer's door".
- **AC2 — a diff adding a migration with no *apply* on its thread is gated, as today.** Every
  reader defaults to no tags and every failure path answers with none, so a caller that has read
  no thread gates exactly as before. Tested by `gated.test.mjs` "gates both files while no apply
  has been spent", "defaults to gated when nothing says an apply was spent", "keeps a snapshot
  gated while its migration is still waiting", "leaves a weakening gated whatever the thread says
  about migrations"; `comments.test.mjs` "reads nothing off a thread the human has not said the
  word on", "reads nothing off an applied note that stands before the word", "reads nothing off a
  reply that only mentions applying in passing"; `consumedApplies`' six refusal cases;
  `permission.test.mjs` "hands back no tags when the thread has no spent apply on it", "hands
  back no tags when the thread could not be read at all".
- **AC3 — an *apply* for a different migration file does not ungate this one.** Matching is by
  tag, and the bookkeeping waits for all of them. Tested by `gated.test.mjs` "does not let one
  migration's apply through for another's", "keeps the journal gated while any migration beside
  it is still waiting", "does not ungate a journal that stands on its own", "reads a migration's
  tag off its path, and nothing else's".
- **AC4 — a database test for a migration not on `origin/main` skips with a warning; the same
  test with the migration on `origin/main` and the column absent fails.**
  `src/test/migration-gate.ts` splits the rule (`gateOf`) from the observation (`landedOnMain`),
  and every case that cannot prove the migration is still waiting runs the tests. Tested by
  `migration-gate.test.ts` "skips only while the migration is not on origin/main", "does not skip
  once the migration is on origin/main and the schema is behind it", "says nothing at all once
  the schema object is there", the four `landedOnMain` cases, and the two `migrationGate` cases.
  Observed in the product as well: with every migration the two suites name on main, they now
  run their tests against Postgres rather than printing a banner — 15 of them when this was
  first written, 21 since `0017` arrived with main at the addendum's merge.
- **AC5 — T3.1's and T1.4's test files use the shared helper and no longer carry their own skip
  path.** Tested by `migration-gate.test.ts` "leaves the unapplied-migration banner to the
  helper", asserted over the two files' own source — over **every** migration each file names to
  the gate since the addendum's merge, T3.1's file now waiting on two.

## Open questions

1. **The tag half of a consumed apply comes from a sentence the run composed — owner `T-next`.**
   Review pass 1's Should 6. The human's `apply` is verified by the guard over the API and cannot
   be fabricated; the tag beside it is read out of the run's own `applied` note, whose file field
   the skill fills from `apply.mjs`'s output. Two steps of misbehaviour would be needed to exploit
   it — a run composing an `applied` note for a migration it did not apply, on a thread that has
   some earlier granted `apply` — and the guard refuses an unprefixed comment and a comment of a
   kind already posted in the claim, so neither step is free. The tighter shape is for `apply.mjs`
   to be the thing whose output reaches the thread rather than a sentence composed around it;
   that is a change to how `applied` is written, not to this gate.
2. **The detector's own five tests answer to no criterion — owner `T-next`.** Review pass 2's
   last Should, and pass 1's Should 4 from the other side. They measure that `loosening.mjs`
   would catch a gate which stopped honouring AC2 and AC3, which is Build 1's last sentence —
   "the loosening detector's other rules are untouched" — rather than a criterion of its own.
   Labelling them TC2 and TC3 would claim they test the gate, which is what pass 1 objected to;
   leaving them unlabelled is what pass 2 objects to. The real gap is that a ticket which narrows
   a restraint has no criterion for *the narrowing being measured*, and that belongs in how
   tickets are cut rather than in this one.
3. **`appliedMigrations` takes the earliest human `apply` on the thread as the grant.** A later
   one does not narrow the window. That is deliberate — a thread can spend more than one apply,
   and the note that matters may precede a second question — but it means the window only ever
   widens as a thread grows. Worth revisiting if a ticket ever carries three migrations across
   two rounds.
