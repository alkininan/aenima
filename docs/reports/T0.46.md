## Defaults taken

- `ADD CONSTRAINT` (a foreign key, a unique, a check, a primary key) is read as additive. The ticket's list in Build 3 does not name a constraint, and `pnpm db:generate` writes one per foreign key of every table it creates — `drizzle/0000` read destructive on those alone, which would hold every generated migration. A constraint adds a rule and touches no row, exactly as `CREATE UNIQUE INDEX` (listed additive) does, and one `DROP CONSTRAINT` reverts it. Cheap to change: one branch in `scripts/run/migration-safety.mjs` and one test.
- `REVOKE` is read beside `GRANT` as additive. Every hand-written migration here takes UPDATE and DELETE off `anon` and `authenticated` for the table it creates; the Objective's line is "destroys or rewrites data", a revoke does neither, and one GRANT reverts it. Left destructive, ten of the eighteen migrations in `drizzle/` would be HOLDs on that line alone. One branch, one test.
- The gatekeeper's file ends in the verdict alone, HOLD's numbered reasons standing above it, as the reviewer's findings stand above `PASS`/`FINDINGS`. Build 1 says both "ends in HOLD" and "HOLD followed by numbered reasons"; the door reads the last line, so the reviewer's shape was taken. `readGate` reads the reasons off the numbered lines wherever they sit.
- `docs/gates/` is gitignored. The file names the pushed commit and the guard binds it to the pull request's head, so it can never be inside the commit it judges; committing it afterwards would move the head. It is the run's own record, like the gate's fingerprint beside the marker, and an ignored file leaves a worktree clean for `prune.mjs` and `branch.mjs`.
- The gatekeeper's rounds are counted by the reviewer's pass rather than a counter of their own: a HOLD's fixes go to the reviewer as the next pass (Build 5 says the round counts toward the three-corrections rule), so `gate-cap.mjs` answers `build` while `review-cap.mjs` has a pass left and `decision` at pass 3. The third HOLD on a claim always lands at pass 3 or past it.
- Step 6 no longer stops. With the gatekeeper deciding MERGE APPLY, a step that stopped on every added migration would make AC3's first half unreachable; a destructive migration is the gatekeeper's HOLD, which `gate-cap.mjs` reads as `migration` and the closer takes to Decision under the narrowed `gated` comment, which `awaitingMigration` now reads as the migration question so T0.26's `apply` carries on. `migration-check.mjs` stays as the lister of added migrations, feeding `gated.mjs`.
- The closer is one agent in two legs — `docs/tickets/<id>.md <branch>` to the push and the gate's green, `… merge` after the gatekeeper — rather than a second agent file, since a subagent cannot invoke a subagent and the orchestrator has to sit between them. `closed <commit>` keeps its meaning for an orchestrator that reads it as the end of the close.
- A diff git cannot read at all is gated (`the diff … could not be read`). With a weakening no longer gating, an empty file list from a failed `git diff` would have opened the door; the loosening corpus's "a merge whose diff it has to work out for itself" entry is what caught it.

## Setup

Say `merge` on this ticket's thread once the pull request is at Review. This diff edits the loosening detector, `scripts/run/loosening.mjs`, which today's guard — main's copy — gates whatever it measures, and the gatekeeper it adds cannot decide its own merge: the guard that would open on the gatekeeper's file is the one in this diff. Under the rule this diff retires the word is read at the next run's step 0, and it is the last `merge` anyone types.

## Out of scope

- The Runs row does not carry the gatekeeper's verdict or the number of HOLD rounds a run took; `runs.mjs` attributes the gatekeeper's tokens to Gate (T0.44's seam) and reads nothing of `docs/gates/<id>.md`. A Gate verdict column and a HOLD count would make the board say how often the second verdict disagrees with the first.
- `migration-safety.mjs` reads `COMMENT ON`, `INSERT`, `DO $$ … $$` and `ALTER POLICY` as "cannot parse", which is the ticket's rule, so a seed insert or a policy edit in a migration is the human's `apply`. Whether any of those belong on the additive list is a call for the next migration ticket that meets one.

## Open questions

1. The `migration` comment kind no longer has a poster: step 6 stopped on every added migration and posted it; now a destructive migration is the gatekeeper's HOLD and the closer posts the narrowed `gated` kind. The composer, its signature and §4's example sentence are kept, since the ticket said `gated` narrows and nothing about `migration`, and old threads still read it. Remove the kind, or make `## Held` post `migration` instead of `gated`?
2. This run's own close cannot follow the protocol it builds: the phase agents registered at session start, so the closer that closes this ticket is the one before this diff, and the guard that judges its merge is main's. The old closer will read `gated.mjs`'s `ok: true` (a loosening no longer gates), try the merge, and main's guard will refuse it on the detector edit and leave the task at Review with no `gated` comment. The `## Setup` line above is what tells you to say `merge`, the last one.
3. `REVOKE` and `ADD CONSTRAINT` are on the additive list by default (above). If either should be the human's word, the change is one line in `migration-safety.mjs` and one test — say so and the next run takes it.
4. A rule this ticket established that binds the harness, for the closer to file in `.claude/rules/harness.md`: a verdict file written for a commit can never be inside it, so a file the guard binds to a head is the run's own record and is not tracked.
