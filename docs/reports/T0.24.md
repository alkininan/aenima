# T0.24 — Apply from a worktree run

Branch `t0-24` · Epic E0.2 Pipeline · Priority Urgent · Type Technical

The deadlock the ticket names was real and had one cause: the boundary had stopped a *word*
rather than a session. `.env.migrate` lives in the primary checkout and is deliberately not
carried into a worktree; the schedule runs every ticket in a worktree; so every run that read a
granted `apply` handed it on to "a run in the primary checkout", which the schedule never
starts. Candidate 1 of the ticket's three is what landed, and the boundary did not move: the
work did.

## ACs implemented

- **AC1** — a granted `apply` reaches the database from a scheduled run in a worktree.
  `scripts/run/apply.mjs` spawns one child whose working directory is the primary checkout and
  whose `--env-file` is that checkout's `.env.migrate`, and hands it the *ticket branch's*
  `drizzle/`, read out of git with `git archive` rather than by checking the branch out — the
  branch was cut before the script that applies it, so entering it would take the script away
  with it. Tests: `apply.test.mjs` "TC1 · AC1 the migrations come from the ref", `exportMigrations`,
  and "TC1 · AC1 a migration drizzle would skip is refused". Verified against the real
  `origin/t3-1` from this worktree: `git archive` yields 16 SQL files including
  `0015_refinement_round` plus the journal, and `primaryCheckout` resolves to `~/dev/aenima`,
  where `.env.migrate` is.
- **AC2** — the worktree session never reads `.env.migrate`, asserted rather than assumed. The
  child's `--env-file` is the primary checkout's path, its working directory is the primary
  checkout, and `DATABASE_URL` is deleted from what it inherits so that file is its only source;
  a decoy `.env.migrate` planted in the worktree is never the one the spec names. Both sides
  scrub any connection string out of what they report. Tests: `apply.test.mjs`
  "TC2 · AC2 the worktree session never reads the admin env file" (five cases) and the two
  `work` scrub cases. Rule (b) of the guard now reads every shape of an apply — `db:migrate`,
  `drizzle-kit migrate`, `db:baseline`, `scripts/run/apply.mjs`, and anything handed
  `.env.migrate` — so the script is not a way round the rule it was written to obey:
  `guard.test.mjs` rule (b), five cases including the neighbours that must stay allowed.
- **AC3** — the word is consumed once. An `applied` comment answers the reply, so the thread's
  `unanswered` empties and `shapeOf` stops reading `apply`; the same reading serves the
  preflight and the guard, because `permission.mjs` calls the same `readThread`/`shapeOf`.
  Tests: `apply.test.mjs` "TC3 · AC3 the word is consumed once", `comments.test.mjs` "consumes
  the word once the run has said it applied".
- **AC4** — the report names the migration applied and its journal index. The worker brackets
  the migrator with drizzle's ledger read as the *set of stamps* it holds, so `applied` is
  exactly the rows that appeared, each as `{ idx, tag }`. Tests: `apply.test.mjs`
  "TC4 · AC4 the report names the migration and its journal index" and the `work` ledger case.
- **AC5** — a failed apply stops the ticket at Decision with the database's own error quoted and
  does not consume the word. The worker returns the error's first line, scrubbed; `readThread`
  reads past a `refused` comment, so the reply that granted the attempt is still unanswered and
  the next run makes it again. Tests: `apply.test.mjs` "TC5 · AC5 a failed apply quotes the
  database and keeps the word", `comments.test.mjs` "leaves the word standing" and "leaves a
  merge standing", `permission.test.mjs` "holds back a refusal the thread still carries".

Two things fell out of the reviewer's reading and are part of the change:

- A migration drizzle's own migrator would pass over in silence is refused by name. It applies
  only what is stamped later than the newest row in its ledger, not what is absent from it, and
  `origin/t1-4`'s `0015_opportunity_keys` (`when` 1788982026724) is stamped older than
  `origin/t3-1`'s `0015_refinement_round` (1789644802697). Whichever landed second would have
  been skipped with `migrate()` returning cleanly, and the run would have posted that it applied
  a file the database never saw.
- A `refused` comment still standing on a thread is not posted again word for word. A word that
  outlives a refusal is retried every run until what stands in the way is settled, and saying
  the same sentence every hour tells the human nothing; a refusal with anything of another kind
  said since is history, and the same error met again posts.

## Open questions

1. **The Done line's end-to-end is not observed here, and could not be** — owner: the next
   scheduled run's step 0a. T3.1's `apply` is granted on the board, but this run's marker names
   T0.24, so the guard reads T0.24's thread and refuses; one run, one ticket. Worse, the hooks
   run `origin/main`'s guard, which does not yet know `apply.mjs`, so running it here would have
   applied T3.1's migration with *no* board word read at all — which is the rule this ticket
   exists to keep. What was verified instead: the export against the real `origin/t3-1`, the
   spawn spec against a real fixture, and `work()` against a fake Postgres. The first run after
   this lands is the observation, and its report is where it belongs.
2. **T1.4 will be refused by name until its migration is regenerated** — owner: T1.4. Once T3.1
   lands, `0015_opportunity_keys` is stamped older than the ledger's newest row; `pnpm
   db:generate` restamps it. This is now visible rather than silent, but it is still work
   somebody has to do.
3. **`pnpm db:baseline` now needs `apply` from the board when a run types it** — owner: none, by
   intent. A human's own terminal is not guarded; only the agent's Bash is.
4. **The change to what a refusal consumes is not measured by `loosening.mjs`** — owner: T-next.
   `verify`/`permitted` is in neither `GUARD_CORPUS` (which injects `permission`) nor
   `DOOR_CORPUS`, so a diff that widens what the board is read to grant is invisible to the
   detector. This diff is such a diff, and it is named here because nothing else names it.
5. **One intermittent red in the node project** — owner: T-next. A single run, under load
   (`tests 89.65s` against a usual `~44s`), reported `1 failed | 1155 passed`; the name was lost
   and it has not recurred in the seven full runs since. The suspects are the child-process
   probes in `loosening.test.mjs` and `hooks.test.mjs`, whose 20s budget is the only thing in
   the suite that load can exhaust. Not introduced by this diff, but seen during it and
   therefore recorded.

## Defaults taken

Said in the claim's one `default` comment, and repeated here: the new script rather than
`pnpm db:migrate` (drizzle-kit takes its migrations folder from the config relative to the
working directory, and the working directory has to be the primary checkout for the credential —
the two cannot both be satisfied by the existing command); rule (b) extended to anything handed
`.env.migrate`, which sweeps in `db:baseline`; and a refusal consuming nothing at *both* words,
`merge` as well as `apply`, rather than only on the apply path AC5 names.
