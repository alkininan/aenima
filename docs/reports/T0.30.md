## Open questions

1. **A session that fires SessionEnd both before and after its claim still makes two rows.**
   Owner `T-next`. The key is the task and the minute; a firing before the run claimed keys on the
   minute alone and a firing after keys on task-and-minute, so they do not match. R-0062 (idle,
   Stopped, 84,424 tokens) and R-0065 (T0.40, Done, 328,209) are that session, one run under two
   keys, and this fix leaves both. The session id would key it exactly and the Runs schema has no
   column for one; adding it is a data-source schema write, which the guard refuses. Deciding
   whether to add that column is the question, and it is the human's.
2. **First write wins, so a resumed run keeps its shorter row.** Owner `T-next`. The ticket chose
   it — "writing a row whose key already exists changes nothing" — and `runs.test.mjs`'s *writes
   nothing for a longer read of the same session* asserts it. The cost is that the row then
   under-reports Outcome, Duration, Tokens and Findings for any run whose hook fired early. The
   alternative is to update the row in place on a later read, which is a different sentence than
   the one the ticket wrote.
3. **What fires SessionEnd more than once for one session is still unknown.** Owner `T-next`. The
   key makes it harmless, so nothing waits on the answer, but the copies are evidence that the
   hook's contract is not what the pipeline assumes, and that assumption is load-bearing elsewhere
   (`release.mjs` runs from the same hook).
