## Open questions

1. **A root dotfile is never looked up.** `classify` skips a single-segment name that leads with a
   dot, so `.gitignore`, `.env.local` and `.worktreeinclude` — 302 occurrences across the forty
   ticket files, ten of which name at least one — are answered `not a path or an identifier`,
   which is false of them. Pass 5 read this as a Must and pass 6 as a Should, and the reason to
   leave it is the one in question 2: the corpus holds nothing else in that shape, but the shape
   is also a bare property reference, and nothing syntactic separates `.git` from `.map`. A count
   of the documents that exist cannot answer for the one nobody has written, so widening this
   needs a rule about the shape rather than another measurement. Skipping costs a missing report;
   widening on the count alone would cost a false one. The choice is now in `classify`'s docstring
   as well as here.

2. **`classify`'s scope came from measuring the corpus, and a count says what the documents that
   exist contain rather than what the next one will.** Every rule in it was chosen against the 36
   files in `docs/tickets/` — that is the right way to choose which shapes are worth handling and
   the wrong way to establish that a shape is safe, which is the lesson the build log already
   carries about the evidence guard's markdown fold. What the measurement cannot see: a ticket that
   introduces a new top-level directory names a path whose first segment is not yet in the
   reference and which carries no extension, and it is skipped rather than reported. That is the
   conservative direction — a missed name, never a false one — and it is written down here so the
   next person widening this brings a count rather than a guess.

3. **A name that exists only in prose reads as present.** The identifier lookup is word-bounded but
   searches the whole reference, documentation included, so a function deleted from the code and
   still named in a report answers `present`. Narrowing to code with a pathspec was the reviewer's
   suggestion and was not taken, because a name in a document is genuinely in the repository and a
   ticket citing one is making a true claim. The case this misses is a rename whose old name
   survives in the build log — which is most of them. Decide it the first time a real rename slips
   through; the trigger is a drift the step should have caught and did not.

4. **Nothing in `.claude/rules/` reached `scripts/run/**` before this ticket**, so step 8's new
   instruction had no destination for a rule about the harness — most of phase 0, this ticket
   included. `.claude/rules/harness.md` is written here as the first one, and it is this ticket
   using its own step 8. Whether the rest of phase 0's harness lessons belong in it is a sweep
   somebody should make deliberately rather than a thing to do in passing. Two lines of the file
   as first written were exactly that sweep done in passing, and both cited a log that did not
   carry the rule; passes 4 and 5 removed one and gave the other its sentence. One line still
   stands on a quotation from the build log rather than a `docs/log/<id>.md` — recorded as a
   Should three times and left for the same sweep.

5. **Nothing checks that a filed rule's citation holds the rule.** `rules.mjs` checks the cited
   path exists; both of the addendum round's Musts were citations that pointed at a real file
   which never says the thing. That is step 2's own defect one level up — a name checked and a
   claim not — and the check that would catch it is a step-8 counterpart to `claims.mjs`. Owner
   `T-next`; the trigger already fired twice here.
