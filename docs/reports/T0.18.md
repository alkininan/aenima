## Open questions

1. **The token's capabilities are the wall; the guard is a reader of commands.** Rule (i) reads
   what a command runs, and a script that imports its write from another file passes it, along with
   the three other shapes filed at Backlog. The integration needs to read content and comments, and
   to insert content for `runs.mjs`'s Runs row. It needs neither *Update content* nor *Insert
   comments*: every board write the pipeline makes goes through the connector. Unchecking those two
   in Notion › Settings › Integrations › *~/dev/aenima pipeline* › Capabilities would make routes 1
   and 2 impossible rather than refused. Even then, *Insert content* could still create a task at
   Ready. Owner: human.
2. **The connector's other writes are not all covered.** `notion-create-pages` with a `template_id`,
   and `notion-update-page`'s `apply_template`, could carry a Status the template holds. Neither
   has been seen in the pipeline. Owner: *Guard the token's remaining routes*, or a ticket of its own.
3. **An edited copy of one of the four scripts that name the API and a write is refused when run
   from a command line.** The four are `guard.mjs`, `loosening.mjs`, `notion.mjs` and `runs.mjs`.
   Only main's copy, byte for byte, is exempt. The pipeline does not meet this: the skill types
   `gated.mjs`, which imports `loosening.mjs`, and tests run under vitest. A ticket that edits the
   detector or the guard and then runs either by hand will. Owner: none; it is the design.
