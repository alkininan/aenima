# T0.22 — Reviewer model fallback

Branch `t0-22` off `origin/main` at `41e2d0f`. The reviewer's model stops being the run's
improvisation and becomes a chain read from the configuration: the model
`.claude/agents/reviewer.md` pins, then `.claude/settings.json`'s `fallbackModel`. A call refused
for credits or availability runs again on the next model of that chain, any other failure is a
stop, and the report names the model of every pass — which `report-check.mjs` now refuses a report
without.

## Defaults taken under §4

Each is a developer surface — a script, its message, a document the run owns — and cheap to
change; all go in the claim's one `default` comment.

1. **The fallback is a script, not only a sentence.** `review-model.mjs` reads the chain from the
   files and the refusal from the error text, so "never a model the run picks for itself" is
   checked in code, as §5 asks of everything countable. It is named in the README's step 5.
2. **The chain begins at the pinned model.** The Build names only "the next model in
   `fallbackModel`"; the model before it is the one the reviewer's definition pins, so the chain
   is that pin, then each fallback, each model once, and a definition that pins none or inherits
   starts at the fallbacks.
3. **What counts as credits or availability** is read from Claude Code's own failure text, taken
   from five runs' transcripts: "Agent terminated early due to an API error: You're out of usage
   credits… (error type rate_limit, HTTP 429, …)". Only an API error counts at all; credits is a
   429, `rate_limit`, usage credits or credit balance; availability is a 5xx status, an
   overloaded model, or a `not_found_error` naming the model. A status is read where a status
   stands, never as any three digits.
4. **A review that could not run stops at Decision with one `refused` comment**, the way step 3's
   claim that cannot go on does: commit and push, the claim's `default` comment if it holds one,
   the `refused` comment, release, Decision, exit.
5. **Each pass starts again at the pinned model** (review pass 1's Must): the pin gets its chance
   on every pass, so credits that come back mid-ticket are used, at the cost of one refused call
   a pass while they are out.
6. **A lost connection is availability** (review pass 1's first Should): the service did not
   answer, which is what availability means here, and the next model is a retry that may reach it.
7. **The model per pass is a table** — `pass · commit · model · verdict` — so `report-check.mjs`
   can read it the way it reads the red-first table, and a pass on a model outside the chain is
   refused. Every report written before this ticket has no such table and would be refused now;
   nothing re-reads them, since the check runs on the one report a run has just written.
