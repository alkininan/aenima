the run owns.

   as §3 has them.

   longer lists blocks nothing. A loop is named on its first Ready member in roadmap order.

## Open questions

1. **The token can speak as the human, and write the board past the guard.** A comment posted
   over the API with `NOTION_TOKEN` comes back authored by the human's own user id, so neither the
   guard nor `readThread` can tell it from a real reply. A status write sent over the API with
   the same token — the capability this run used to trash its fixtures — never reaches the
   connector the guard stands at. Nor is every connector write guarded: rule (h) covers
   `notion-update-page`, `notion-create-pages` and `notion-create-comment`, and the connector's
   `notion-update-data-source` could rename the Status options under every task at once (pass 3,
   Should 2). A run could put `merge`, `apply` or `ready` on a thread from a Bash script.
   This has been true for `merge` and `apply` since T0.11. The connector's three writes that
   carry a status or a comment are now guarded. The token's routes and the data-source write are
   filed: *Guard the token and duplicate routes*. Owner: that task.
2. **The board's Priority description** still reads "MoSCoW. Default Should." The options are
   already Urgent · High · Medium · Low · None. Editing a property description on the board is left
   to the human. Owner: human.
3. **Notices count against the clarifying cap.** `readThread` counts every prefixed comment after
   the first as a clarifying round. A waiting, loop or Urgent notice on a task that later stops at
   Decision therefore uses up a round. The `stale` and `default` comments already do the same.
   Owner: T-next.
4. **A resolved notice comes back.** The API lists open discussions only. If the human resolves
   the discussion a notice sits in, the next run no longer sees it and posts it again. Owner:
   T-next; §5 already says to resolve nothing until the run has answered.
5. **Every status write but Backlog now costs the guard two API reads.** Without the token, a
   run's Done, In progress and Review writes are refused too. A run without the token claims
   nothing, so only step 0c's Done writes are newly lost. Owner: human to confirm that is the
   intended failure.
6. **product-spec §11** says Backlog → Ready is the one transition aenima never makes for itself.
   The dev board now makes it on the human's written word. The dev board is not the product, and
   the product spec is gated, so it is untouched. Owner: human.
7. **T2.8 was merged after this run merged main into its branch.** The only conflict was the
   generated list, and the suite was green on the result. The human's `merge` was given on the
   branch before that commit. Owner: human, if that reading of `merge` is too wide.
8. **The Urgent notice can land twice** (pass 3, Should 1). "The newest" is chosen afresh each run
   and only that task's thread is read. With four Urgent tasks, the newest claimed first puts a
   second notice on the next newest. At exactly three, AC4 holds. The fix is to drop the notice when
   any Ready Urgent task's thread already carries one, with a four-task test. Owner: T-next.
9. **A rich-text comment could pass the prefix check and read as the human's** (pass 3, Should 3,
   unsure it is reachable — the connector was only seen taking `markdown`). `commentText` reads an
   equation or mention part as empty, while the API returns its text. The fix is to refuse unless
   the first part is text beginning with the prefix. Owner: T-next.
10. **§5's token paragraph says less than the guard does** (pass 3, Should 4). It names a merge, an
    apply and a Ready write as refused without the token, but the guard refuses every status write
    but Backlog. The fix is one phrase: "or any status write but Backlog". Owner: T-next.
11. **A notice waits while a human reply is unanswered** (pass 3, Should 5). §5 step 1 does not say
    so, and a thread stopped at the two-round cap never gets its notice. The fix is one clause in
    §5 step 1. Owner: T-next.
12. **The reviewer ran on Opus.** The reviewer definition's own model, Fable, was out of usage
    credits for this session, and each of the three passes stopped once at the 30-turn limit and
    was resumed with no briefing. Owner: human, to know.
