# T0.36 — Regenerate the build log at merge

## ACs implemented

- **AC1** — a branch whose only conflict with main is in generated files merges: main is merged
  in, the sections regenerated, the gate green on the result. `scripts/run/premerge.mjs` merges
  `origin/main` into the ticket branch with a merge commit; a conflict confined to
  `docs/build-log.md` is settled by merging the written passages three ways with the generated
  bodies blanked and then running `log-index.mjs` over `docs/log/`, which after the merge holds
  both sides' entries. Step 0's merge path and step 9 both run it, and both gate and push the
  result before anything merges. Tests: `premerge over a temporary repository` — "merges main in
  and rebuilds the list from both sides' entries", "leaves the build log equal to a fresh
  generation, holding both tickets", "keeps prose the branch added that main never touched",
  "keeps prose main added that the branch never touched", "merges written passages both sides
  moved, in places that do not overlap", "does nothing to a branch that already carries main".
  Verified beyond the fixture: run against `origin/t0-26`, `origin/t0-30` and `origin/t0-34` —
  the three branches the Objective names — each answers `ok: true, merged: true, resolved:
  ["docs/build-log.md"]` with no conflict markers and `log-index.mjs --check` clean.
  **And run for real on this branch, in the addendum round**: `premerge.mjs` against `origin/main`
  at `ede2da8` answered `ok: true, merged: true, resolved: []` — T3.2's build-log line and
  T0.36's sat in different hunks, so git joined the two regenerated lists itself and the
  resolution path was never needed. `log-index.mjs` on the result writes nothing: the merged file
  already equals a fresh generation holding both entries, which is what AC1 asks of the tree that
  lands. The step is the same either way — main goes in first, the result is regenerated, and the
  gate runs on it before anything merges.
- **AC2** — a conflict in any other file is refused, names the file, and pushes nothing. The
  merge is aborted and the checkout left as it was found; `files` names the conflicted paths and
  `why` says what kind of conflict it is. A conflict *inside* the build log but over written
  passages both sides rewrote is refused the same way — settling it from either copy would drop
  somebody's words without saying so. **"Pushes nothing" is about the merge, not about the
  branch**: what a refusal withholds is the merged commit — nothing new is written to the branch
  and nothing reaches main — while step 9's "every exit pushes" is pass 1's Must 2, the work
  already committed going to the remote so the board's Commit names a commit somebody can fetch.
  A refused premerge leaves the checkout exactly as it found it, so that push carries the branch
  as it stood. Tests: "refuses a conflict in a file nothing regenerates,
  and pushes nothing", "refuses a build log whose conflict is outside the generated sections",
  "refuses a dirty checkout rather than merging over it", and the `mergeWritten` block.
- **AC3** — guidelines §5 states the step at 0 and 9, and its version is bumped to v1.24, past
  the v1.21 and v1.23 that still-open branches hold. The skill carries the same step at both
  places, since the skill is what a run actually reads. Tests: `the protocol carries the step`.

makes it again once the branch merges cleanly*. It was this ticket's own branch that went first.
