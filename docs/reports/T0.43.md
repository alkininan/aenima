# T0.43 — Deploy check falls back to the vercel.app address

The deploy check asked aeni.ma alone, and aeni.ma has not resolved since 2026-09-24 — the `.ma`
registry holds no NS records for it — so every check since answered unknown while merges kept
landing. `health.mjs` now asks the addresses `deploy` in `.claude/board.json` names, in order: the
domain, then the deployment's production alias on Vercel, `https://aenima-ae-nima.vercel.app`. A
name that does not resolve is skipped and never counted; the outcome is the first address's that
answers at all.

One thing the ticket did not know changed what "answers" means. From outside, every
`*.vercel.app` address of this project sits behind Vercel Authentication. Measured on 2026-09-28
with Node's `fetch` (`redirect: "manual"`, no user agent): `/sign-in` and `/app` each answered
`302`, `location: https://vercel.com/sso-api?url=…&nonce=…`, `set-cookie: _vercel_sso_nonce=…;
Secure; HttpOnly`, `server: Vercel`; curl got the same. Read as an answer, that is `/sign-in
answered 302 rather than 200` — **down** — and the first run after this merged would have reverted
a healthy merge, and every one after it. So Vercel's login is read as Vercel answering in the
deployment's place: skipped, named in the unknown line, never down. With Vercel's Protection
Bypass for Automation secret in `.env.local` the check is let through; without it, which is where
this machine stands today, the check answers unknown and names both addresses — the true answer.
Run live at close: `https://aeni.ma does not resolve; https://aenima-ae-nima.vercel.app: /sign-in
went to Vercel's login and /app went to Vercel's login: the site could not be reached from this
machine, which is no verdict on the merge; asked again next run`.
