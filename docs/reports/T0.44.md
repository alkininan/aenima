# T0.44 — Phases as subagents

A run is now a thin orchestrator and a subagent per phase. `/ticket` keeps steps 0 and 1 and the
orchestration between phases; the planner (`.claude/agents/planner.md`) does step 2, the builder
(`builder.md`, `builder-medium.md`) steps 3 and 4, the reviewer (`reviewer.md`,
`reviewer-medium.md`) step 5, and the closer (`closer.md`) steps 6 to 9 and every stop. The step
text moved out of the skill verbatim — a test compares every paragraph against the skill as it
stood at `a76a501` — and three paragraphs the ticket rewrote on purpose are named in that test
with the Build item that rewrote them. The orchestrator writes each phase into the run marker
(`scripts/run/phase.mjs`), and the guard's new rule (j) holds each phase to its reach. The review
loop is capped at three passes, counted by `scripts/run/review-cap.mjs` off the verdict file. The
Runs row splits Tokens across Plan, Build, Review, Gate and Close and names its Route, read from
the orchestrator's `phase.mjs` commands and the subagents' meta files.

**Which of the two the harness allowed (Build 7):** two frontmatters. The Agent tool this session
was handed takes `description`, `prompt`, `subagent_type`, `model`, `run_in_background` and
`isolation` — no effort — so an effort is an agent file: `builder` and `builder-medium`,
`reviewer` and `reviewer-medium`, each twin one body under a different name and effort, which
`phases.test.mjs` holds identical.

## Changed since this ticket was cut

Nothing drifted: the Spec line names documents without versions, and guidelines v1.30 and
build-guide v2.10 were current at claim. One thing the ticket did not know: `ruleLetters` in
`loosening.mjs` put match objects, not letters, into its Set, so a rule marked in more than one

three. Fixed here, with a test, since the ticket requires (j)'s corpus entries and the coverage
check reads through it.

## Open questions

1. **The real run the Done line asks for cannot happen before this closes, so the line is yours
   to waive** — owner: you, then the first run after the merge. The hooks run `origin/main`'s
   guard, so rule (j) is inert until this merges, and subagent types register at session start
   (build log, open question 35), so this session cannot invoke the planner, the builder or the
   closer. The diff is gated — it edits the loosening detector — so it does not merge itself on
   any verdict: it waits for your `merge` at Review, and that word is where the Done line is
   waived or held. The first `/ticket` after the merge is the real run; its Runs row, with its
   phase columns, is the evidence to read before the next change to this pipeline.
2. **The Runs database needs its new columns before you say `merge`** — owner: you. `Plan`,
   `Build`, `Review`, `Gate`, `Close` (number) and `Route` (select: medium, xhigh, fallback). Until
   they exist every row the SessionEnd hook posts is refused by the API for naming properties the
   database lacks, and `runs.mjs` reports that as `posted: false` from a hook nobody watches — the
   row is lost, not queued. The connector cannot add them: the guard refuses a data source's
   schema change (rule (h)). See the setup comment.
3. **The phase is model-writable** — owner: T-next. The marker is a file the orchestrator writes;
   a phase agent that ran `phase.mjs` itself would move its own reach. Each agent's file says what
   its phase may do, and the guard reads the marker, not the agent. If Claude Code's hook input
   names the calling agent, the guard could read that instead.

## Defaults taken

- The Shoulds task is named `Shoulds from <id>`, not `<id> Shoulds`: a Name that leads with an ID
  is claimed under that ID, and this ticket's number and branch are its own (§7).
- Shoulds standing at the last pass are filed whichever pass it was, a pass-1 PASS included, so no
  Should is dropped for having been found early.
- The reviewer is handed `docs/tickets/<id>.md pass <n>` — the pass beside the path, the one thing
  the cap and the pass's scope need, and no prose.
- The orchestrator's own tokens go to the phase the marker named when each message was written,
  and to Plan before the first phase — so an idle run is all Plan, and the five still sum to
  Tokens.
- "Source" in rule (j) is every path outside the repository's own `docs/`; the close phase may
  write there (the report, the log entry), and nowhere else.
- The route reads the ticket's own-section paths before the build and adds the diff's after it;
  the three routes are named for their effort — `medium`, `xhigh`, `fallback`.
- Every stop goes through the closer, since in its own phase the builder may not push or post.
- The planner and the closer take their tools as a denylist — `disallowedTools: Edit, Write,
  NotebookEdit` — where Build 1 lists an allowlist. Both read or write the board through the
  connector, and the connector's tools are named after its server, which differs from one machine
  to the next (`mcp__<server>__notion-fetch`; the guard matches them by pattern for the same
  reason), so an allowlist cannot name them portably. What the denylist leaves open beyond the
  ticket's list is held by rule (j) while the marker names their phase. The builder's list is the
  ticket's, exactly.
- Build 5's "the closer runs the gate itself before the push as step 9 already does" is read as
  step 9 already does it: the gate runs on the pushed tree, before the self-merge.
