## Open questions

1. **`.worktreeinclude` and `.gitignore` are ungated and unmeasured.** Build item 2 takes both out
   of the gated set and names four detector families, none of which reaches them. Guidelines §5's
   capability boundary rests on `.worktreeinclude` not carrying `.env.migrate`; a diff appending it
   would hand every worktree the admin credential and self-merge. Guard rule (b) still refuses
   `db:migrate` without the word, so this is a second layer gone rather than the boundary. A rule
   in the detector's shape — the after side names no `.env` file the before side did not — would
   close it. Owner: `T-next`.
2. **`CRITERION` is not ticket-scoped.** `testsLoosened` reads a deleted test naming `AC1` as
   replaced by any added file naming `AC1`, and every ticket has an AC1. Scoping it would need the
   ticket id in the test file, which is a convention this repository does not have yet. Owner:
   `T-next`.
3. **Build item 2's hook, gate, deleted-test and door bullets have no AC.** Five of the six ACs
   name the guard, the paths and the detector; the other rules are built and tested but nothing in
   the Criteria retires them. About twenty cases in `loosening.test.mjs` therefore name a Build
   item rather than a criterion. Worth an AC7 on the ticket. Owner: the ticket's author.
4. **A diff that adds a guard rule is gated until the corpus grows to cover it.** That is Rule 2 as
   written — "a rule with no corpus entry fails the check" — and the corpus is always
   `origin/main`'s, because the guard runs main's copy, so a diff cannot vouch for its own new
   entry. It means every guard-rule addition needs one human `merge`. Recorded rather than
   questioned: it is the ticket's own choice, and the alternative is a diff marking its own
   homework.
