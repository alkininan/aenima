## Findings

1. **Must** — The toast is at the top-left of the viewport, on a `Canvas`-coloured strip.
   `src/components/ui/Toast.tsx:152` shows the viewport region as a `popover="manual"`, and the UA
   stylesheet's `[popover]:popover-open { inset: 0; width: fit-content; height: fit-content;
   background-color: Canvas; color: CanvasText }` now applies to it. `TOAST_VIEWPORT_CLASSES`
   (`src/components/ui/variants.ts:643-645`) sets `fixed inset-x-0 bottom-[24px] px-[24px]` and
   nothing else, so `top` stays `0` and, with `height: fit-content`, the over-constrained `bottom`
   is the inset that gets ignored; `width: fit-content` with `left: 0` does the same to `right`.
   Measured at 1280×900: `[role="status"]` rect top 0, bottom 70, left 24; the region is
   `:popover-open`, computed `top: 0px; width: 213.95px; height: 70px; background-color:
   rgb(18, 18, 18)`. Design-spec §8.20: "Bottom-centre, 24 above the viewport's bottom edge …
   glass recipe". Every C-20 test passes because none reads a rect. Smallest correction: add
   `top-auto w-auto h-auto bg-transparent` (and `overflow-visible`) to `TOAST_VIEWPORT_CLASSES`,
   and one browser assertion in the `C-20 · toasts` block (`e2e/panel-geometry.spec.ts:221`)
   that the toast's bottom is the viewport's height less 24 and its centre is the viewport's.

2. **Must** — The contents never fade: the `morph-content` name sits on a `display: contents`
   element, which the engine does not capture. `src/components/ui/Panel.tsx:291`
   `<div ref={contentRef} className="contents">` is what `runMorph` names `morph-content`; an
   element that generates no box is skipped by capture, so no `::view-transition-group(morph-content)`
   or `::view-transition-new(morph-content)` is ever created and the rule at
   `src/app/globals.css:1105` is dead. Measured mid-morph (60ms in): `document.getAnimations()`
   holds `::view-transition-group(morph)` and `::view-transition-image-pair(morph)` only, while the
   wrapper's computed `display` is `contents` and its `view-transition-name` is `morph-content`.
   Since `::view-transition-new(morph)` is `display: none` per §6, the panel's contents are
   invisible for the whole `--t-med` and pop in at `finished` instead of fading over the last
   `--t-fast` — §6 Morph: "The container morphs; the contents fade … the contents carry a second
   name and fade in over the last `--t-fast` of the open." `src/lib/morph.test.ts` only checks the
   name is set. Smallest correction: give the wrapper a box (`className="block min-w-0"` or
   `flex flex-col`) so it is captured, and extend "grows the group from the trigger's box toward
   the panel's" (`e2e/morph.spec.ts:98`) to assert `getAnimations()` mid-morph includes
   `::view-transition-new(morph-content)` running `aenima-fade-in`.

3. **Should** — C-17's Shift+Tab clause, and the menu's Tab, have no browser test.
   `e2e/morph.spec.ts:233` "C-17 · where focus is" covers Tab for the select only; nothing
   presses Shift+Tab anywhere and nothing tabs out of a menu. Both work (measured above), so no
   outcome changes today; the menu's path works because `Menu.tsx:140-143` refocuses the trigger
   synchronously and lets the browser's own Tab carry on from there, which the comment at
   `src/components/ui/Menu.tsx:77` — "Escape and Tab both hand focus back to the trigger" —
   describes as the end state rather than the mechanism. Add the two assertions and reword the
   comment. C-16's "a tooltip raised inside a modal stays up while the pointer crosses onto it" is
   likewise only exercised on the page, not inside a modal.
