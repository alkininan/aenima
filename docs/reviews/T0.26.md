the sentence is posted.** The migration `ungate` now reads `… waits for you either way — say

one is the wrong one. Carried from pass 3 (Should 2) and sharpened: the fix is to end the clause at
"waits for you", or make the second half `say "merge" here`.

**Should 2 — `src/test/migration-gate.ts:43-44` reads every non-zero `cat-file` status as "not
landed", and git's status for a missing path is the same as for any other fatal.** Observed here:
`git cat-file -e origin/main:drizzle/9999_nope.sql` prints `fatal: path … does not exist in
'origin/main'` and exits **128**, not the 1 the fixture at `migration-gate.test.ts:52-56` pins;
128 is also what git exits with for an object it cannot read past a `rev-parse` that succeeded.
`return blob.status === 0` sends both to `false`, which is the answer that buys a skip, while the
doc comment at `:36-38` says "the lookup itself failing" answers true — that holds only for
`blob.error`, a spawn failure. I weighed Must against the ticket's rule that a skip on main must be
impossible, not unlikely, and tag Should: TC4's four cases hold as observed (present → 0, absent →
128), and the residual is a broken or partial object store, which is no configuration this pipeline
runs in. Smallest correction: ask `git ls-tree --name-only origin/main -- <file>`, read landed as
status 0 with non-empty stdout, and any non-zero status as true; and set the fixture to 128 so it
models git.
