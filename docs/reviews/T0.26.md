## Shoulds

**1. `docs/guidelines.md:394-396` contradicts itself about where the tag comes from.** The
sentence reads "`gated.mjs` reads the spending off the task's own thread and not off anything a
run says about it — your reply beginning with `apply`, and the run's own `applied` note after it
naming that migration's tag". The `applied` note *is* something a run says about it, and it is
the only source of the tag. The report's open question 2 is that exact gap, so the spec should not
read as though both halves were the human's. Smallest correction: "…off the task's own thread
rather than off the run's account of itself in session — your reply beginning with `apply`, and
the run's own `applied` note after it naming that migration's tag".

**2. `scripts/run/gated.mjs:118` still says the two-word rule in the copy the human reads.** The
ungate string is `'a migration is applied by hand, so this one waits for you either way — say
"apply" on the thread and the run that applies it lands the ticket with it'`. "Either way" was the
second way — the `merge` this ticket removed — and there is no longer one; pass 2's Must corrected
that sentence in five other places and missed the one that is output rather than comment. The
composer around it (`scripts/run/comments.mjs:426`) then closes with 'say "merge" here', so one
comment names two words for one decision. Smallest correction: drop "either way" — "a migration is
applied by hand, so this one waits for you — say \"apply\" …".

**3. `src/test/migration-gate.test.ts:130-132` still binds AC5 to the banner's wording.** It
rejects only `process.stderr.write` calls whose text contains the path the file names to the gate.
A re-introduced inline skip worded without a path — "the table does not exist yet" — passes, which
is the drift TC5 exists to stop. Pass 2 raised this; keying on the file rather than on the literal
`drizzle/00` fixed the maintenance half and not the wording half. Binding the rule would be
asserting that `gate.skip` is the only thing the file's `skipIf` reads, or that no
`process.stderr.write` beside the offline one survives.

**4. `src/test/migration-gate.ts:40` trusts the local `origin/main` ref.** `landedOnMain` asks
git and nothing fetches, so a checkout that has not fetched since the migration merged reads
"not landed" and skips — the one thing the rule exists to make impossible. It holds in the
pipeline, where step 0 fetches; it does not hold in a person's stale checkout. One sentence in the
helper's doc comment saying the observation is as fresh as the ref would price it honestly.
