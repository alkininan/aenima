## Findings

Three Musts, ranked, then six Shoulds.

1. **Must: `currentCycle` decides the cycle from one arbitrary row, out of a read that is
   documented as unordered.**
   - `src/lib/authoring/rounds.ts:124`:
     `const stored = mine.find((round) => round.cycleNo === newest)?.baseSectionHash ?? null;`
   - `src/db/queries/refinement.ts:25` says "Every round on one artifact, every section,
     **unordered**", and the query at lines 46–50 carries no `order by`. `find` therefore takes
     whichever row Postgres returned first.
   - Rows of one cycle can hold different baselines, so which row it lands on changes the answer.
     The reachable path needs no legacy data: `run.ts:121-124` yields `baseSectionHash === null`
     when the newest human version holds no section with that id — the ordinary case for a section
     the author drafted and no human has ever written. Round 1 is then written with a null
     baseline; the human later cuts a version that does hold the section, `currentCycle` reads the
     null and holds the cycle (lines 124–125, as documented), and round 2 is written at the same
     cycle with a real hash. From then on, one read of the ledger says `closed` and the next says
     `revise` on cycle 2 — the same rows, a different row order.
   - Smallest correction: make the decision over every row of the newest cycle rather than one —
     turn the cycle when `mine.filter((r) => r.cycleNo === newest).some((r) => r.baseSectionHash
     !== null && r.baseSectionHash !== baseSectionHash)` — which is order-independent and is what
     lines 100–110's comment already claims the function does. A test on a mixed cycle (`round(1,
     { baseSectionHash: null })` beside `round(2)`, asserted in both array orders) reddens it.

### Shoulds

1. **No red-first record exists at this commit.** `docs/reports/T3.2.md` is absent, so I cannot
   confirm that any of the 26 new tests (9 in `rounds.test.ts`, 4 in `sections.test.ts`, 3 in
   `loop.test.ts`, 4 in `run.test.ts`, 6 in `refinement.db.test.ts`) was observed failing first.
   §5 step 8 refuses the report without the table; this is a note that the table is still owed,
   not a claim that the tests are bad.

2. **AA1 has no trigger in the product.** `readHumanBaseline` (`src/db/queries/refinement.ts:110-127`)
   reopens a cycle only when an `artifact_version` row carries `authored_by_kind = 'human'`. The
   only writer of one in the repository is `scripts/seed.ts:767`; `writeRound` writes every
   revision as `'agent'::actor_kind` (`refinement.ts:195-199`), and `scripts/refine-file.ts:162`
   writes its version 1 as an agent too — so in the one runnable end-to-end path the baseline is
   always null and no cycle can ever turn. The path that would move it is AC1/AC2's confirmed or
   edited echo, which is finding 2's unbuilt half. Record the dependency explicitly — "the human's
   answer must land as a human-authored `artifact_version` or AA1 never fires" — so the dock claim
   cannot miss it.

3. **The key deviates from the addendum's literal wording and the deviation is recorded only in
   code.** `docs/tickets/T3.2.md:76` says "Key the closure to (artifact version, section, check)";
   what ships is keyed to the section's text in the newest *human-authored* version
   (`rounds.ts:15-24`, `run.ts:83-86`). The argument for it is sound and I would not change the
   code — keying on any new version would let the loop's own revisions reopen what they just
   closed, and §6's cap would never bite. But it changes what the ruling means (an agent version
   never reopens; a human edit to a *neighbouring* section never reopens), so it belongs in the
   report's defaults and the claim's comment, per §5 step 4, not only in a docstring.

4. **Three test names do not point where they claim.** `src/lib/authoring/run.test.ts:246`,
   `describe("the cycle's baseline — TA1 → AA1")`, collides with T3.1's TA1 at
   `src/lib/authoring/sections.test.ts:21` — every other T3.2 block disambiguates with "T3.2's".
   `src/db/refinement.db.test.ts:230-257` puts two T3.2 TA1 tests inside a describe titled "the
   round ledger's key — TA3 → AA3", so their full names carry T3.1's label. And T3.2's AA2 has no
   titled test at all: its only marker is the comment at `run.test.ts:128`, while a grep for
   "TA2 → AA2" lands on T3.1's blocks in two other files. Title the AA2 test
   `TA2 → AA2` and prefix the two T3.2 blocks as the rest are.

5. **The truncation record is write-only.** `readRounds` (`src/db/queries/refinement.ts:36-64`)
   selects neither `reason_truncated` nor `evidence_truncated`, and `StoredRound`
   (`rounds.ts:66-93`) has no field for them, so nothing in the codebase can read back that an
   objection was cut. The row holds the fact, which is what AA3 asks for; but "nothing about this
   path may be silent" (`docs/tickets/T3.2.md:92`) ends at the surface that will show the open
   question, and that surface cannot currently see it. Add the two columns to the read when the
   dock needs them, or note the gap as owned by the dock claim.

6. **Two small ones.** `roundCount`'s cycle-less form (`rounds.ts:130-137`) is documented as
   answering "how many times has this been argued over", but it returns the highest round number
   across cycles — 3, not 5, for a ledger of a spent 3-round cycle and a 2-round one — and it has
   no caller outside tests; either fix the sentence or sum per cycle. And `fit()`
   (`loop.ts:114-118`) cuts by UTF-16 code unit, so a quote whose 2000th boundary falls inside a
   surrogate pair stores a lone surrogate that the driver will replace, leaving an `evidence`
   string that no longer occurs in the section; cutting back to the last whole code point costs one
   line.
