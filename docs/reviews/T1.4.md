## Findings

1. **Must — nothing records that any new test was seen failing first.** `docs/reports/T1.4.md` is
   not in the tree, and the red-first record is not in the commit message or the ticket either.
   §5 step 4 asks for "new logic has tests observed failing first, the mutation and the count
   recorded per test", and step 8 refuses the report without it. Twenty-two new tests land in this
   diff across five files; not one of them has a row. Until that table exists every new test here
   is evidence about nothing. I note the report is step 8 and this review is step 5 — the record
   is still owed before close, and T0.17's pass 1 raised the same thing at the same point.
   Smallest fix: write `docs/reports/T1.4.md` with the per-test table (the mutation that reddened
   it, the count that went green), including a row for the six tests in
   `src/db/opportunity-key.db.test.ts` saying what was observed against a database with 0015
   applied, or that they have never run.

2. **Must — AC5 has no test.** Criterion 5 is "An opportunity with no items renders a stated empty
   line rather than an empty region". The line exists — `src/app/o/[key]/page.tsx:79`,
   `<p className="type-ui-body text-n-secondary">{t.opportunity.noItems}</p>` — and nothing
   anywhere asserts it: `grep -rn "noItems" src --include=*.test.tsx --include=*.test.ts` returns
   nothing, and the ticket's Tests section names no test for it. The nearest test,
   `opportunity.test.ts:200` "returns an empty item list rather than failing when nothing is
   linked", asserts `items` is `[]` in the query layer, which is the input to the branch and not
   the branch. `t.opportunity.items` and `t.opportunity.backToList` are untested on the same page,
   which leaves AC7 half-held for that surface.
   Smallest fix: lift the section out of `page.tsx` into an `ItemSection`-shaped component beside
   `ItemLine.tsx` and give it a dom test with both arms — the sentence when the list is empty, the
   lines when it is not — and add the Tests line naming AC5.

3. **Must — the query documents an order it does not ask for.**
   `src/db/queries/opportunity.ts:57` says of `items`: "In creation order, which is the order they
   were bet on." `getOpportunityByKey` (`:105`–`:112`) issues `select` → `eq` → `eq` →
   `maybeSingle` and never calls `.order`, so the embedded `item` rows come back in whatever order
   Postgres produced them and the page's list can reorder itself between two reads. Every other
   list read in this layer orders explicitly — `item.ts:108`, `item.ts:332`, `product.ts:30`, and
   `listOpportunities` itself at `opportunity.ts:36`. The test file even records `order` calls and
   then asserts none of them.
   Smallest fix: `.order("created_at", { ascending: true, referencedTable: "item" })` on the read,
   with a test asserting the call — or delete the sentence from the comment, since AC3 asks for no
   order.

4. **Must (I am less sure of this one than of 1–3) — the summary claims §4's subtitle slot and
   then breaks its rule.** `src/app/o/[key]/OpportunityHeader.tsx:18` says "The summary sits in
   §4's subtitle slot", and `:20` says it "wraps rather than truncates". design-spec v2.17 §4,
   Subtitle slot: "ui-body, `--n-secondary`, 8 below the title … **One line; it truncates rather
   than wraps on narrow widths.**" The same diff's `ItemHeader.tsx:45`–`:46` reads the rule the
   other way for its own subtitle — "in §4's subtitle slot: ui-body, --n-secondary, one line,
   truncating rather than wrapping" — so the two headers now disagree about the same slot. The
   spec is not silent here, so CLAUDE.md's "Where the spec is silent: stop and list the question"
   does not cover it, and AGENTS.md makes an undeclared departure a bug: "A stopgap is legal only
   when it is recorded in the build log as an open question with a phase owner."
   Smallest fix: add `truncate` to the summary line, matching `ItemHeader`; or, if a wrapping
   problem statement is the right call, record the departure from §4 as a build-log open question
   with a phase owner and say so in the report.
