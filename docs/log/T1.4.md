# T1.4 — the opportunity page, and the key that makes its URL sayable
_2026-09-16T01:10:00Z_

T1.4 closes build-log open question 9. `src/lib/routes.ts` has reserved `/o` since T1.1 and could
not build it: `opportunity` carried `id`, `workspace_id`, `product_id`, `title` and `summary`, and
nothing in that list goes in a URL a person reads out. The stated fix was to mirror `item.key` — a
`key_prefix` counter assigned by trigger, never a uuid route — and `drizzle/0015_opportunity_keys.sql`
is `drizzle/0005_item_keys.sql` one table over, statement for statement: the column added nullable,
backfilled per product in creation order with `row_number()` over `(created_at, id)`, set NOT NULL,
`UNIQUE (workspace_id, key)` as the backstop on the MAX+1 race, the same shape CHECK, and
`app.assign_opportunity_key()` on `BEFORE INSERT` overwriting `NEW.key` unconditionally so a key a
client supplies is ignored rather than honoured.

**Mirroring `item.key` exactly means `soc-3` can name an item and an opportunity in the same
product.** The counters are independent and the unique constraints sit on different tables, so
nothing prevents it; `/i/soc-3` and `/o/soc-3` tell the two apart and a person saying "soc-3" does
not. That follows from what the ticket and open question 9 both asked for, twice, and it is the one
property of the design worth a second look while there is still nothing in the wild to migrate. It
is held by a test rather than left as a remark, so the day it is judged not worth it, something
says what changed.

The page itself shows what it can honestly show. §2 makes an opportunity "a problem or outcome …
holds an evidence pile that outlives individual bets", and there is no evidence table yet — so
`/o/<key>` renders the problem and the bets: key, title, summary and product in the header, then
the items linked to it, each a link back to `/i/<key>`. Nothing stands in for the pile.
`getOpportunityByKey` fetches the whole tree in one request with the artifacts `deriveStage` needs,
because listing items means knowing every item's artifacts and the per-item alternative is the N+1
that works on three rows and falls over on a real product. An unknown key and a key in another
workspace are the same 404 by one code path — `getItemByKey`'s rule, for `getItemByKey`'s reason.
And the item header's opportunity line, plain text since T2.4 because a uuid href would have
defeated the whole reason the routes are short, is a link.

**The ticket stops here, at Decision, with its schema half unapplied.** §5 step 6: a migration is a
change to a shared database and a human applies it. That is not a formality on this machine —
`.env.local`'s `DATABASE_URL` is not the table's owner, so even trialling the DDL inside a
rolled-back transaction came back `must be owner of table opportunity`. The credential boundary
worked exactly as designed, and the consequence is that `0015` was read against `0005` rather than
executed.

Which forced the one genuinely new decision in this ticket. The trigger's tests can only be written
against an applied schema, and the Stop gate runs the whole suite at every stop in every worktree —
so a db test that failed hard on the missing column would have reddened *every* run in the repo
until someone applied the migration, and "you have not applied a migration" is a sentence a broken
suite cannot say. `src/db/opportunity-key.db.test.ts` reads `information_schema` for the column and
skips with a loud stderr banner naming the file to apply, which is the discipline `rls.db.test.ts`
already uses for an absent `DATABASE_URL`, one cause over. It starts checking for real the moment
the column lands, and nothing in it is conditional on what the trigger *does*: the assertions are
the real ones or the file is silent. **Whether that is the house pattern or this ticket's exception
is open question 40** — a test that skips itself cannot fail for the reason it exists, and the
alternatives (a suite project outside the Stop gate, or a preflight that fails the *run* on an
unapplied migration in the tree) both say the true thing somewhere else. Decide it at the next
migration, which is the first point where copying this or not is a choice somebody makes.

`src/db/database.types.ts` carries one hand-written block for the same reason — the generator reads
the live database and there was none to read. It is `item.key`'s shape exactly, which T2.4's
regeneration already vindicated for `item.key` itself, and the run that applies `0015` owes a
regenerate-and-diff.

Three review passes. Pass 1 found four Musts: no red-first record, AC5's empty state asserted
nowhere, a query documenting a "creation order" it never asked the database for, and a summary
claiming §4's subtitle slot while wrapping where §4 says it truncates — two headers disagreeing
about one slot, which is the drift a slot exists to prevent. Pass 2 found two more, and the first
was the sharpest thing either pass said: `e2e/item.spec.ts` asserted *the opposite of criterion 6*.
That test existed to stop a link being added to `/o/<key>` while `/o/<key>` was unbuildable — it
was the guard on open question 9 — and this ticket built the thing it guarded, so the test and its
comment had to invert with it. Pass 2's second Must was that the red-first record was per file
where the guidelines say per test: six tests seen red against twenty-one passing. Redone as
twenty-three scripted mutations, one at a time, each naming the tests it reddens. Pass 3 was cold
and passed, with five Shoulds; three were small enough to fix on the spot — a comment that
described what the stretched link does not do, an embed ordered on `created_at` alone where the
migration's own backfill tie-breaks on `(created_at, id)` for exactly that reason, and a copy of
`toArtifacts` that is now one export.
