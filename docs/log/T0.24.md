# T0.24 — Apply from a worktree run
_2026-09-20T17:20:00Z_

T0.24 — apply from a worktree run. **A granted word can always be acted on.** T0.10 put the
admin URL in one file in one place and kept it out of worktrees; T0.11 made `apply` a word the
guard reads off the board. The two met badly. The schedule runs every ticket in a worktree, a
worktree has no `.env.migrate`, so every run that read a granted `apply` handed it on to "a run
in the primary checkout" — and the schedule starts none. T3.1's `apply` had been granted since
this morning with nothing on the machine able to act on it, and every migration ticket behind it
would have queued the same way.

The boundary was right; what was wrong was that nothing could act on the human's word. So the
work moved rather than the credential. `scripts/run/apply.mjs` makes the apply as one child
process whose working directory is the primary checkout and whose `--env-file` is that
checkout's `.env.migrate`: the credential is read where it lives, into that child and nowhere
else, never copied into the worktree, never put on the run's own environment — `DATABASE_URL`
is deleted from what the child inherits so the file is its only source — and never printed,
because both sides scrub a connection string out of anything they report. The migrations come
from somewhere else again. The branch that carries a migration was cut before the script that
applies it — `origin/t3-1` has no `apply.mjs` — so entering that branch to read its `drizzle/`
would have taken the machinery away with it, which is the same deadlock one step later. The ref
is read instead of entered, `git archive` into a directory of its own, the way the hooks read
`scripts/` from `origin/main`. Machinery from the checkout the run stands in, migrations from
the ref, credential from the primary checkout, and no two of the three have to be the same tree.
The guard's rule (b) reads every shape of the thing now — `db:migrate`, `drizzle-kit migrate`,
`db:baseline`, that script, and anything handed `.env.migrate` — so a script written to obey the
rule is not a way round it.

Two things the review found are the better half of the change. The first: drizzle's own migrator
applies a migration only when it is stamped *later* than the newest row in its ledger, not when
it is absent from it, and the two branches waiting on this pipeline each generated an `0015` —
T1.4's stamped 1788982026724, T3.1's 1789644802697. Whichever landed second would have been
passed over in silence, `migrate()` returning cleanly, and the run would have posted that it
applied a file the database never saw. The ledger is now read as the set of stamps it holds
rather than as a high-water mark, so the apply can say which entries the migrator would skip and
refuse rather than report. The second: a refusal answers nothing. It reports an attempt that
failed, so the word that granted the attempt outlives it and the next run makes it again once
what stood in the way is settled — you say `merge` or `apply` once, and a conflict or a Postgres
error is not you taking it back. What does not repeat is the sentence: a refusal still standing
on a thread, word for word, waits.

The end-to-end the ticket asks for is the one thing this run could not do. Its marker names
T0.24, so the guard reads T0.24's thread; and the hooks run main's guard, which does not yet
know this script, so applying T3.1's migration here would have been an apply with no board word
read at all — exactly the rule the ticket exists to keep. The first run after this lands is the
observation, and it belongs in that run's report.
