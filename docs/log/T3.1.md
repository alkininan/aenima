# T3.1 — Author-critic loop
_2026-09-20T17:40:00Z_

T3.1 — the author-critic loop. **§6's two-round cap is a ledger, not a counter.** The author
drafts a section, the critic tests it blind against the checks in play, every objection binds to a
real check and quotes the section it may change, and the third disagreement stops being an
argument and becomes an open question the human owns. Everything deterministic in that sentence is
code with a test — binding, evidence verification, the scope wall, the round count — and the two
model calls are the only judgement in it.

Three things no spec defined had to be settled before any of it could be stored, and all three are
schema, so the first claim stopped at Decision rather than guessing (§4). **A section is a `##`
heading block**, its id the heading's slug with a numeric suffix on collision, which is a parse
over the stored body and leaves `artifact_version.content` and §5's protocol fingerprint alone.
**An open question is a round row marked `surfaced`** — no open-question table, so T3.2's Open
Questions section and T3.4's rendering read these rows rather than a second copy of the same fact.
**One append-only row per round**, unique on (artifact, section, check, round number), because a
row per artifact version cannot stay append-only: a refused revision cuts no version, so the next
round tests the same one and would need an UPDATE the trigger refuses.

Migration 0015 then put three more choices in front of the human, for the same reason the first
three went there: an enum value cannot be dropped once applied. **`held`** is the fourth outcome —
the author returns the section unchanged because it has nothing new to say without a fact nobody
supplied. Without it an unchanged revision has to be recorded as `revised`, cutting a version
identical to the last and re-running §5's checks on text that did not change, or not recorded at
all, which lets the author hold its ground forever because no round is ever spent.
`revised_version_id` makes "which edit answered this objection" a join rather than a guess by
timestamp, and `outside_sections` is the ledger's answer to "why was this round spent".

**Scope is a wall because §5's cache is real.** The author's call receives only the scoped
section; its revision is spliced back into the document, the whole document is parsed again, and a
revision that touched anything else is refused and the round is spent. A wandering fix would
invalidate check results cached against sections nobody asked to re-run — which is why the Build
made this a wall rather than a request, and why `checkRevisionScope` refuses a whitespace-only
change outside the scope, a section added or removed, and a reorder, while letting the scoped
section itself move.

**Two provider limits shaped the calls, and both were found by paying for them.** The generation
tier runs at the provider's default effort, the model thinks by default, and thinking counts
against `max_tokens`: the first draft came back `schema-invalid`, cut off mid-JSON, having spent
its whole 4,000-token ceiling on reasoning. Truncated JSON reads as a flaky provider rather than
as a ceiling, which is the expensive way to learn what T2.3 already wrote down one layer up. The
ceilings are now 12,000 for the critic and 16,000 for the author, in the scorer's proportion.

**The ticket took three claims and two stops, both of them the design working.** The first stopped
on the three schema questions; the second built the addendum and stopped on the migration, because
a run's credential cannot apply one. The word `apply` then sat on the board for three days with
nothing on the machine able to act on it — the defect T0.24 was cut to fix — and this third claim
is the first run to pick a ticket back up from a granted `apply`, from a worktree, exactly as
T0.24's `apply.mjs` intended. `refinement_round` exists, its nine database tests were reddened one
by one and run against Postgres, and `database.types.ts` regenerated against the project came back
identical to the block written by hand before the table existed.

Two smaller things rode along. Preflight now regenerates the route types whenever they are
**stale**, not only when `.next/types` is missing: a directory that exists says nothing about
which tree generated it, and this ticket's own worktree arrived carrying types that named a route
not on main, so typecheck failed before anything had been touched. `route-types.mjs` stamps the
route files, the Next config and the Next version it generated from and regenerates on any other.
And `guidelines` is v1.17 rather than the v1.16 it was written as: T0.24 took that number while
this ticket waited, so `origin/main` is merged into the branch and the one conflict — the header
both changes wanted to head — is resolved with both entries in it.
