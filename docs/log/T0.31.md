# T0.31 — Read bundled shell -c flags
_2026-09-23T06:58:00Z_

The guard reads commands, never text, and `parse()` is what turns a Bash string into the commands
a rule then matches on. A shell's `-c` is the seam where that reading recurses: what follows it is
not an argument but another command line, so `parse()` calls itself on it. It looked for the flag
as a bare word, `args.indexOf("-c")`. Short flags cluster — `bash -lc`, `sh -ec`, `bash -xc` — and
read as text a cluster is not `-c`. The recursion never happened, and the command line inside was
invisible to every rule below: `pnpm db:push` past rule (a), `git push --force` past rule (d), a
write to the board's API past rule (i), and — as the review measured rather than assumed — rules
(b), (c), (e) and (f) with them. T0.18's cold reviewer found this and filed it as a Should; it sat
on the board for a day as the one hole in the guard you could walk through by typing a letter.

The fix is one predicate. What took three rounds was getting its edges right, and both corrections
were the same mistake pointing opposite ways. First: `shellRun`, the other site that asks whether a
shell carries `-c`, scanned the whole argument tail — and the tail holds the *script's* arguments,
not only the shell's. `bash post.sh -lc` looked like a shell running a command string, so the file
was never opened at all. A tightening ticket had loosened rule (i), and `loosening.mjs` could not
see it, because its corpus runs `bash ready.sh` with no arguments. Second, one pass later: bash
spells its long options with one dash as much as two, and four of them are a run of letters holding
a `c` — `-norc`, `-rcfile`, `-restricted`, `-protected`. Each read as a cluster, and `findIndex`
stopped at the first, so the *real* `-c` behind it went unread. `bash -norc -c 'pnpm db:push'` was
refused on main and allowed here.

Those four are named now, and `parse()` follows every word that reads as the flag rather than the
first — so an option nobody thought of still cannot stand in front of a real `-c`. The fourth name
arrived after the reviewer's PASS: pass 3 pointed out that the set held three and the comment above
it claimed that was all of them, which was a false sentence about a security boundary. It was
fixed, and the report says plainly that the PASS did not read that commit. The change only adds a
name to an exclusion set and a test, so the guard refuses strictly more than the tree that passed,
never less — which is the only direction in which a post-verdict edit is safe.

The ticket asked for clusters *ending* in `c`. Every shell here reads a `c` anywhere in the
cluster: `bash -cl '…'` runs its string as surely as `bash -lc '…'` does, which was run rather than
recalled. Reading only the last letter would have left the same hole one letter away, so the
matcher takes the whole cluster. That is a developer surface and one regex — cheap to undo, so it
was taken as a default rather than stopped on.

What this leaves is the thing worth saying twice: every one of the three refused → allowed
transitions found here was invisible to `scripts/run/loosening.mjs`, which answered `ok: true`
throughout while rule (i) stood open. The detector measures the restraints by running them over a
fixed corpus, and the corpus holds no bundled shape. Each transition was caught by a reviewer
running both sides by hand. A corpus that knew these shapes would put the measurement where the
close reads it, rather than where a careful reader happens to look.
