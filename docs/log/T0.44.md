# T0.44 — Phases as subagents
_2026-09-27T22:42:59Z_

A run was one session carrying every tool result it had seen from preflight to merge, and the one
part of it that ran in a fresh context — the reviewer — was the part that kept finding real
defects. Now the session is a thin orchestrator: steps 0 and 1, then a planner, a builder, the
reviewer and a closer, each a subagent with its own tools and its own slice of the protocol,
moved out of the skill verbatim and held so by a test that reads the skill as it stood at
`a76a501`. The handoff is the files the run already writes and one typed last line; every stop
goes through the closer, the one phase that pushes, merges and writes the board. The orchestrator
writes each phase into the run marker, and the guard's rule (j) holds the phase to its reach. The
review loop is three passes counted off the verdict file by `review-cap.mjs`; the builder and the
reviewer run at the effort the route table in `.claude/board.json` names, as two agent files each,
since the Agent tool takes no effort per invocation; and the Runs row splits Tokens across Plan,
Build, Review, Gate and Close and names its Route.

Two things the ticket did not see. The marker is one file for every checkout, so a phase read off
it bound every session in the repository — a scheduled run in `build` would have refused your own
push from the primary checkout — and review pass 2 caught it: the phase binds the run's own session
and no other. And `ruleLetters` in the loosening detector had never deduplicated anything: it put
match objects into its Set, which was invisible while each rule had one marker and plain the moment
rule (j) had three. The diff edits the detector, so it waits for your `merge`; that word is also
where the Done line's real run is waived, since no run can take one through phases that register
at session start behind a guard that runs from main.
