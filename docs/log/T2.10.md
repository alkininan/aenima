# T2.10 — Surface no-longer-applicable closures
_2026-09-16T04:55:00Z_

T2.10 — build log open question 14, answered. A gap the applicability engine closed because §4's
condition stopped holding is the one closure a person might disagree with: the safety layer
turning off is a judgment about the artifact, not an observation that a check now passes. The
ledger has recorded it since T2.3 — `gap.closed`, reason "no longer applicable" — and nothing
showed it. It shows now on the `not-asked` line in the meter's expansion: §5's exact quoted gap,
then the question, directly beneath the condition that stopped holding.

**The check line won over the gap card, and that was the ticket's one real choice.** Open question
14 said "beside the move that argues applicability", and §5's first negotiation move is Phase 3 —
there was no control to sit beside. The gap list is what §13 says an item *owes* a person, and a
closed gap owes nothing; putting one there would have fought T2.4's narrowing and produced a card
with no move on it. The check line already speaks about applicability — it carries the pack's
condition, negated, because the check is on that line precisely for being false of this artifact.
The closure and its question complete that sentence rather than starting a new one. `gapHasCard`
still answers false for `closed`, so exactly one element per gap wears `gap-<id>` and the anchor
rules are untouched.

**The notice is gated on the run's own `not-asked` state, which is what keeps it in the present
tense.** A check can come back: a later version brings the condition with it, the check is asked,
and the line is `unclear` or `passed`. Pointing at the old closed gap there would be a sentence
about a state that has already passed, and about a debt a fresh gap has already replaced. Reading
the gate off the line rather than off the gap is the whole of that correctness.

**The reason is a ledger fact, so the read goes to the ledger for it.** `gap_resolution_shape`
gives a closed row a time, no name and no note; `passed` and `no longer applicable` are the same
row. `listGapsClosedAsNoLongerApplicable` filters `activity` on workspace, `subject_table = 'gap'`,
the gap ids the item holds, `action = 'gap.closed'` and `metadata->>reason`. No column was added
and no migration was written — the schema's own doctrine is that the gap holds the current answer
and the ledger holds how it got there, and this is the first caller to take it at its word.
Inferring the reason from the state around it would have been right most of the time: a gap closed
by a pass, on a check a later run stopped asking, reads exactly like one the engine closed.

A fresh-context review returned one Must and six Shoulds at pass 1, and five more Shoulds at pass
2; the Must was the report's own red-first record, raised at pass 1 on T0.17's and T0.20's
precedent because it is the one claim a diff cannot answer. **The Should worth keeping is the
collision.** A check can lose the argument twice — leave the denominator, come back and fail, leave
again — which puts two gaps closed as no longer applicable on one check id, and a map keyed by
check shows one of them. The first draft showed whichever `getItemByKey` returned last, which is
the same answer most of the time and silently the wrong one the rest. `noLongerApplicableByCheck`
keeps the **newest**, because the line it renders on is about the denominator now. It orders by
`Date.parse` rather than by string: both stamps come from one column in one format, so text order
agrees with time order today and would stop agreeing quietly the day anything handed it a stamp
written another way — and a stamp that will not parse sorts as oldest rather than becoming a `NaN`
that makes every comparison false and lets the first row win by accident.

`/dev/item` carries a sixth fixture gap so the treatment can be looked at, and `run-view.test.ts`
holds the fixture to the same rule its gap pairings already obey: only closures `reconcileGaps`
could have written may be staged. The run's `prd-19`, closed because its check came to pass, is
the control that must keep rendering nowhere.
