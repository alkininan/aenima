# T0.26 — Applied migrations merge themselves
_2026-09-23T00:55:00Z_

A migration ticket asked for two human words where one decision had been made. `apply` is the
schema decision — the database is shared, and changing it is not a run's call. `merge` at Review
asked about it again, after the fact, with the migration already applied: T1.4's `0016` landed on
the shared database from the branch, and the code that reads `opportunity.key` then sat at Review
for a second word about a column that already existed. The gap between the two words is the
database ahead of main, which is the one direction that helps nobody.

So the gate narrows. A migration leaves the gated list when the claimed task's thread carries a
**spent** apply for that file, and stays on it otherwise. Spent is two things and both are read
from the thread by code: the human's reply beginning with `apply` — `mentions`, the same test the
guard makes before it lets the apply through — and, after it, the run's own `applied` note naming
that migration's tag. Either half alone says something weaker. A word nobody acted on is a word
still outstanding; a note no word granted is a run vouching for itself. The tags come out of the
answer rather than the question, because the `migration` comment names its file *before* anything
has happened to it, and a reader that took the tag from there would ungate a migration on the
question alone.

The matching is per file, which is not a detail. T3.1's `0015` was applied days before T1.4's
`0016`, on another thread and another branch, and a gate reading "some apply" would have landed
the second on the first. The journal is the one path that cannot carry a tag of its own, so it
goes only when every migration beside it in the diff has — and never on its own, where there is
no migration an apply could have been for.

**The narrowing sits above `isGatedPath`, and that is where the detector could not see it.**
`loosening.mjs` measures restraints by running them on both sides of a diff, and its path corpus
asks `isGatedPath` whether `drizzle/0022_x.sql` is gated. That function is untouched here and
goes on answering yes; what changed is the judgement above it. A copy of `gatedDiff` that read
any apply, or no apply at all, as answering for any migration would open the gate with every path
still on the list, and `pathsLoosened` would report nothing. So `gatedDiff` gains a corpus of its
own — three shapes a narrowed gate must still gate — measured on both sides like the guard's
rules and the two doors. It is the same lesson T0.21 wrote down one layer lower: a restraint that
nothing runs on both sides of a diff is a restraint that can be deleted unseen.

The guard's two doors read one fetch. `verify` was already reading the claimed task's thread to
look for `merge`; it now hands back the spent applies from that same read, and `judge` passes
them to `reviewed`. Nothing asks the board twice, and the two doors cannot disagree about what
the thread says. The skill's step 9 asks the same question from a command line through
`consumedApplies`, which fails closed on every path: no marker, no token, no board file, a thread
that would not load — each one answers with no tags, and a migration nobody could read a thread
about is gated exactly as before.

**Build-log open question 40 is ruled.** A database test guarding a schema change may skip while
its migration is still on a branch waiting for the apply — between the run that writes a
migration and the run that applies it the column exists nowhere, and failing hard there reddens
every run in the repo until somebody applies it, which is a suite saying "you have not applied a
migration" by breaking. That licence ends the moment the file is on `origin/main`. A migration
that has landed is one every checkout has, so a missing column is no longer a ticket in flight;
it is a database behind the code, and the honest answer is red. `src/test/migration-gate.ts` is
the rule in one place, and every case that cannot *prove* the migration is still waiting falls
the same way: a ref that will not resolve, a git that will not run, a lookup that fails — none of
them buys a skip, because a skip on main is a failure hidden. T3.1's and T1.4's test files call
it and carry no skip path of their own; with both migrations on main, all fifteen of their tests
now run for real for the first time.

One test had to change that is not this ticket's subject. T0.28 asserted the guidelines header
read `1.20` exactly — a fact about the afternoon it was written, not about §7 — so every later
bump reddens it and the only move available is to retype the number, which arms the same trap for
the next ticket. It now asserts the rule the assertion was reaching for: the header carries a
version, and it has never gone back behind the one §7's rule arrived in. The build log has said
this before, about a test that pinned two layout numbers instead of the rule relating them: pin
the rule, not the pair of values that currently satisfy it.

Guidelines to v1.21. §4 carries the sentence — a migration takes one word, and the ticket that
carries it merges itself once that word has been spent — and §2, §3 and §5 steps 6 and 9 say the
gate the same way, so no surface describes a permission the code no longer asks for.
