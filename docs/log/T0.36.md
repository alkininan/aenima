# T0.36 — Regenerate the build log at merge
_2026-09-23T10:55:00Z_

T0.32 gave the build log two sections written from `docs/log/`, which was the right answer to
two tickets editing the same list: each adds a file, and a script rewrites the list. What it
did not answer is what happens when both branches then carry a regenerated `docs/build-log.md`
into a merge. They disagree on it every time, and the second to arrive is refused on that file
alone. T0.26 and T0.34 were both refused that way after their `merge` was given, and the
refusal comment promised that "the next run makes it again once the branch merges cleanly" —
which nothing was going to make true. A ticket that merges itself at close escaped only because
nothing lands between its push and its merge.

So the branch takes main before it merges, at both places a merge happens: step 0, where a
`merge` on the thread is acted on, and step 9, where a run merges its own work. `premerge.mjs`
merges `origin/main` in with a merge commit and reads the conflict before touching it. Every
conflicted path must be a generated file; then what the two sides wrote *outside* the generated
sections must itself merge. The blanked texts go to `git merge-file`, and the list is rebuilt
on top by `log-index.mjs` over the entries the merge brought in — so the file that lands is the
file a fresh generation would have written, with both sides' prose in it. Anything else aborts
and names the files, and the task stays at Review.

Getting the second half right took all three review passes, and both corrections were the same
mistake made smaller. Comparing the two sides refuses a branch that added a paragraph main never
touched. Comparing all three for equality refuses a branch that wrote in one place while main
wrote in another — which is a clean merge by any reading, and is what the build log's written
passages actually do. The equalities answer only what they can answer without merging; the rest
is git's question, and git is what answers it. The lesson is narrow and worth keeping: a script
that decides whether two texts can be combined is writing a merge algorithm, and there is one
in the box.

The step does what it was built for — run against `t0-26`, `t0-30` and `t0-34`, each now merges
clean — but it does not get those three onto main. They conflict with main on the guidelines
header and on the version assertion this ticket rewrote, and `premerge.mjs` refuses both by
name because neither is generated. One conflict traded for two, honestly reported: the header
is an append-only block every version bump writes to, and it has no answer yet of the kind the
build log got. That is filed, as is the larger thing this run walked into — the shared database
carrying a migration from a ticket that then stopped, which leaves `pnpm test` red on main for
everybody and no check anywhere that notices.

That last one closed the way it was diagnosed, and closed this ticket with it. T3.2 was the
ticket that had stopped; a `merge` on its thread landed it, `0017` reached main's schema, and
the suite went green in every checkout at once. This branch then took main in with the script it
had just built — no conflict at all, as it happened, because T3.2's line in the generated list
and this ticket's sat in different hunks and git joined them itself — ran the gate on the
result, and merged itself on its own PASS. The mechanism's first real use was getting its own
author onto main, and the refusal comment it was written to make true came true on its own
branch first.
