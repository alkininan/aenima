# T0.46 — The gatekeeper decides the merge
_2026-09-28T09:40:12Z_

Two human words stood between a passed diff and main, and one of them asked a question the
pipeline could already answer. `apply` is the schema decision and stays: the database is shared,
and no revert takes a dropped column back. `merge` was the word for a diff that weakens a
restraint, and T0.26 waited four days across five refusals for one the reviewer had already
passed. So the word becomes a second verdict. The gatekeeper is a subagent at medium effort with
a fresh context and one file it may write, `docs/gates/<id>.md`, ending in `MERGE`, `MERGE APPLY`
or `HOLD`. It asks five questions and no more — does the diff do only what Build asks, is every
loosening the detector lists named by the reviewer and asked for by the ticket, does the PASS
stand on this commit, do the cited sections still say what the ticket assumed, is every migration
additive — and the last is not its to answer: `migration-safety.mjs` reads each migration and says
additive or destructive in code, and the model may only be stricter than the script. The guard's
second door reads two files now, both written for the pushed commit the pull request's head is;
`WORDS` is `apply` and `ready`, and a reply beginning `merge` is a note. A HOLD is findings —
fixed, re-reviewed, re-gated, counted toward the three passes by `gate-cap.mjs` — and the third
stops at Decision with the reasons quoted. A destructive migration is a HOLD that goes straight
there and waits for `apply`.

Three things the ticket did not settle, and the cold review found. A gatekeeper that wrote
`MERGE` where the migration in the diff wanted `MERGE APPLY` was routed to the merge leg, which
applies nothing, so main would have carried code reading a column nobody created — the landing
T0.26 closed; it goes to Decision now, because the apply door opens on `MERGE APPLY` alone and
widening it is an open question. The closer promised that a refused merge would be made again at
the next close, and no step made it: with `merge` gone there is no word to repeat the attempt on,
so a refusal leaves the task at Review until a change reply or a hand merge, and the documents say
so instead of promising otherwise. And the gatekeeper's model fallback existed in prose only;
`review-model.mjs` now reads the chain from whichever agent file it is handed.

One rule this ticket wrote down: a verdict file written for a commit can never be inside it.
`docs/gates/` is ignored by git, like the gate's fingerprint beside the marker, because the guard
binds the file to the pull request's head and committing it would move the head. And one thing
the close met that the ticket's Done line foresaw: this diff edits the loosening detector, main's
guard gates whatever the detector it runs measures, and the copy that could open on the
gatekeeper's file is the copy in the diff. The checkout's `gated.mjs` answers `ok: true` for its
own loosening; `origin/main`'s answers `ok: false`; the door is main's, so main's was the one
asked. The ticket waits at Review for `merge`, the last one anyone types. Guidelines to v1.32,
build-guide to v2.12.
