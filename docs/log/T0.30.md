# T0.30 — Runs rows written once
_2026-09-23T05:50:00Z_

The Runs database is the pipeline's only account of what it costs to run — park rate, findings per
ticket, the four-week weight tuning all read it — and it was counting some runs three times. The
ticket named four copies. The query found twenty-two, across fifteen runs described by
thirty-seven rows, and three of the twenty-two had been written the day the ticket was cut, after
it was cut.

What makes them copies rather than second runs is that they are exact. R-0056, R-0057 and R-0058
each say 101,250 tokens and eight findings and 20.6 minutes, to the digit. A second run of the
same ticket would differ everywhere; only a second *read of one transcript* is identical. So
`post` was being handed the same transcript more than once, and writing the whole run again each
time.

The first instinct was to name the cause — a session cleared, resumed or exited fires SessionEnd
again — and the reviewer took that apart twice. A `/clear` starts a new transcript with a new
first timestamp, so a firing after a clear would key anew and make a second row rather than a
no-op: the sentence was not just unsourced, half of it was wrong in a way that would have
misdirected whoever read it next. The branch now says only what the evidence carries. It is a
small thing and it is the whole lesson of the ticket: the fix does not need the cause. Keying the
row on what identifies a run — the task it claimed and the minute it started — makes every read
after the first a no-op whatever fired it, and a key that does not depend on a diagnosis cannot be
broken by getting the diagnosis wrong.

The minute, not the timestamp, because a Notion date property keeps no seconds: the row is written
with `11:22:30` and reads back `11:22:00`, and a key comparing those as strings would find no
match and write the copy it exists to prevent. Both sides are floored in `runKey`. The reviewer
pushed for writing the floored minute instead, which is tidier and would have rewritten T0.12's
own assertion about what the row sends for no change in what the board stores; it was declined and
recorded.

Two things this does not fix. A session that fires the hook both before and after its claim still
makes two rows, under two different keys — R-0062 and R-0065 are one session, idle-and-Stopped at
13:49 and T0.40-and-Done at 18:22. Keying that exactly wants the session id, and the Runs schema
has no column for one; adding it is a data-source schema write, which the guard refuses, so it is
a question for a human rather than a thing to build. And first write wins, so a run whose hook
fired early keeps the shorter row forever.

The twenty-two copies are still there. Nothing in a run can delete a Notion page — the connector
offers create, update, duplicate and move and no archive, `update-page` has no `in_trash`, and §4
refuses a Notion API write from a command line, which is the only other road. So AC2 is written
down rather than done: the report names every row to keep and every row to remove, and the ticket
waits at Review for a hand that can do it. The key stops the set growing meanwhile, which is the
half that mattered.

**The addendum round, 2026-09-23.** The hand came: the twenty-two are gone, and AC2 is met — the
four the ticket names by number answer nothing now, and the three it says should remain all do.
Main came into the branch the same day; `premerge.mjs` refused the merge because the conflict
reached `docs/guidelines.md` and `scripts/run/next-id.test.mjs`, which is the script being right
about what it owns, and the reply had already handed those two over. The header's version line is
v1.26 rather than the v1.25 the arithmetic suggests, because `origin/t0-26` is holding v1.25 and
§7 says a branch holding a number keeps it. The assertion this branch had moved to a pinned `1.21`
went back to main's floor, which learns the same lesson without a number in it.

What is left is smaller and the same shape. TC2 asks a wider question than AC2 — no two rows alike
anywhere in Runs — and seven copies written on 2026-09-23 still answer it. They are not the fix
failing; they are the fix sitting on an unmerged branch while the SessionEnd hook runs the
checkout's own `runs.mjs`, which at a tree of main has no key. They stop the moment this lands,
and the seven are named in the report for the hand that cleared the twenty-two.
