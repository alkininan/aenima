# Product spec v1.11 — the Loop folded in
_2026-10-20T10:28:00Z_

The Loop by Sociera operating handbook (v1.4) — the process system built for Sociera's own
toolset, Teams, Notion, Fireflies, Figma, CodeRabbit, Azure DevOps and Amplitude — read against
the product spec section by section and folded in. Mechanics went into the spec; one team's
operating rules (meeting rhythm, the 25% reserve, the Loop Scrum) stayed in the handbook.

Twelve rulings settled the contradictions, and the spec header carries them. The ones that
changed a law's reading rather than adding a mechanic: aenima v1 still ends at handover, with the
measurement appointment the one thread that runs past it; the actor doing the work moves a
ticket and an observer never does, which reconciles the Loop's "people set every status" with the
board's self-moving run without touching law 1; pre-signature editing stays free and the Loop's
frozen change sets apply only to post-signature patches, so there is still exactly one gate; the
Loop's typed-name rule is satisfied by reading a word from the record it was written in, never
from the model's account, so `ready`, `apply` and `merge` stand.

Vocabulary, researched and ruled: **suite** for a runnable test set (ISTQB's word), **gate** for
a merge or release condition (Azure DevOps, Sonar and GitHub all say it), **status** for a
ticket's lifecycle position (Linear's word; an item keeps *stage*), **snapshot** kept for the
interview one-pager (Torres's word) and the version tuple's Figma element renamed *Figma
version* (Figma's own history is versions), **mirror** for the Loop's *Current*, **registry** for
the per-product record of who speaks for what. A tool's own result keeps the tool's word.

Design spec v2.24 adds the six terms to C-34; build guide v2.12 adds §3 rule 9, the Notion write
as Phase 4 will build it. Build-log open questions 41–48 name what each deferred item owes and
which phase owns it. `feature-prd` still carries check 7's v1.10 prose until its next version
(open question 41).
